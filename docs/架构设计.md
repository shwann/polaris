# 北辰技术架构（v3.1：全 TypeScript + SQLite，已确认）

日期：2026-11-11。北辰（Polaris）要做成一个 **Claude 插件**：装上以后，Claude 能管理任何项目的需求和开发进度，用户在本机或手机上看星图看板。本文先讲整体架构（第 0 节），再讲前端工程（第 1～9 节）。实现以当前源码为准。

## 0. 整体架构：一个插件，四个部分，一个数据库

| 部分 | 是什么 | 谁用 |
|---|---|---|
| **Skill** `skills/polaris/` | 告诉 Claude 什么时候记、记什么：需求进来、派工、完成、合入、发版、等用户决定 | Claude |
| **斜杠命令** `commands/` | `/polaris:status` 看现状、`/polaris:req` 记一条需求、`/polaris:sync` 同步当前工作、`/polaris:mirror` 更新线上镜像 | 用户 |
| **命令行 `polaris`**（TypeScript，Node 自带 `node:sqlite`，打包成单个 `polaris.mjs`，不用装依赖） | **数据唯一的读写入口**：增改需求和任务、记动态、登记发版、加系统、检查、备份、起本机看板、生成镜像 | Claude、用户 |
| **看板前端** `web/` | 星图看板，构建成单个 HTML，由命令行提供本机服务或打包成镜像 | 用户 |

**数据**：所有系统共用一个 SQLite 数据库。北辰本来就是所有系统的总览，一个库装下最自然。

**为什么用 SQLite**：

| 需求 | 做法 |
|---|---|
| 需求与任务多对多 | 关联表加外键 |
| 漏项和统计查询 | 直接写 SQL |
| 多会话同时写 | 每条命令一个事务，WAL 模式加忙等待，不会写坏 |
| 字段合法 | 表结构约束：非空、枚举 CHECK、外键 |
| 字段级历史 | 修改记录表 |
| 依赖 | Node 22.13 起自带 `node:sqlite`，不用装任何包 |

**以后可选**：
- 把同一套命令包成 MCP 服务，让 Claude 以工具形式直接调用。第一版不做。
- SessionStart 钩子已提供只读摘要，可用 `POLARIS_HOOK=off` 关闭。

### 0.1 数据放在哪

```
~/Documents/polaris-data/          数据目录（可用环境变量 POLARIS_HOME 改）
  polaris.db                       数据库（另有 -wal、-shm 两个运行时文件）
  backup/                          文本备份，独立 git 仓库
    polaris.sql                    整库 SQL 导出（每次写入后更新并提交）
  build/mirror.html                生成的线上镜像
```

- **代码和数据分开**：插件代码仓库（现在的 `polaris/`）不放数据，插件更新或重装不会碰数据。
- **只放本机**：数据库不要放进 iCloud 或网盘同步，多台机器同时打开容易损坏。在手机上看，用线上镜像。
- **命令行找数据目录**：先看 `--home`，再看环境变量 `POLARIS_HOME`，最后用默认 `~/Documents/polaris-data/`。
- **项目和系统怎么对上**：项目仓库里可以放一个 `.polaris.json`，写明它属于哪个系统。在这个项目里调命令时，系统可以不填。

### 0.2 表结构（第 1 版）

字段名用英文，界面上的中文名由前端映射。时间一律存 ISO 8601 带时区。

| 表 | 主要字段 | 约束与说明 |
|---|---|---|
| `systems` 系统 / 星座 | `key` 主键、`constellation`、`name`、`note`、`sort` | 第一个系统就是现在的“北斗” |
| `system_apps` 正式版本 | `system_key` 主键并引用系统、`version`、`build`、`released_at`、`backend`、`backend_label`、`backend_build`、`skill`、`model`、`rollback`、`next`、`next_note`、`ref` | 与系统一对一，天枢面板读这里 |
| `releases` 发版记录 | `id`、`system_key`、`version`、`released_at`、`ref`、`note` | 系统内版本号唯一 |
| `requirements` 需求 | `id` 主键、`system_key`、`title`、`body`（Markdown 正文）、`source`、`priority`、`status`、`scope`、`owner`、`created_at`、`updated_at` | `source`：客户、用户、评审、缺陷；`priority`：P0、P1、P2；`status`：提出、待澄清、已确认、已排期、开发中、待验收、已完成、搁置 |
| `requirement_acceptance` 验收标准 | `req_id`、`seq`、`text`、`met` | 一条需求多条，可逐条勾选 |
| `requirement_refs` 关联文档 | `req_id`、`seq`、`ref` | 计划路径、PRD 章节、链接 |
| `tasks` 任务 | `id` 主键、`system_key`、`code`、`title`、`lane`、`status`、`sort`、`progress`、`detail`、`needs`、`owner`、`ref`、`waiting_since`、`shipped_in`、`target_release`、`unverified`、`created_at`、`updated_at` | `lane` 就是现在的 group：planned、doing、waiting、release、risk、done（换名是因为 group 是 SQL 保留字）；`progress` 0～100 |
| `task_steps` 任务步骤 | `task_id`、`seq`、`name`、`state` | `state`：done、doing、blocked、todo |
| `task_requirements` 需求与任务的关联 | `task_id`、`req_id`，联合主键 | 多对多，两边都有外键 |
| `events` 动态 | `id`、`at`、`system_key`、`text`、`task_id`、`req_id` | 页面上的“最近动态”。命令行写入时自动生成一条，也可以手写 |
| `changes` 修改记录 | `id`、`at`、`actor`、`op`、`entity`、`entity_id`、`field`、`old`、`new`、`batch` | 每次增删改都逐字段记一条，同一条命令共用一个 `batch`；`actor` 是谁改的（Claude 会话名或“用户”），由 `--actor` 或环境变量 `POLARIS_ACTOR` 给出 |
| `schema_version` 表结构版本 | `version`、`applied_at` | 迁移用 |

**连接设置**：
- 打开外键检查；
- WAL 模式；
- 忙等待 5 秒；
- 每条写命令用 `BEGIN IMMEDIATE` 开一个事务，业务数据、`changes`、`events` 在同一个事务里一起提交，要么全成，要么全不成。

### 0.3 备份、恢复与迁移

- **文本备份**：每次写命令成功后，用 `iterdump` 把整库导出成 `backup/polaris.sql`，并在 backup 仓库里提交，提交信息就是这次的动态文字。这样 git 里能看出每次改了什么，也能用它整库重建。
- **恢复**：
  - `polaris restore backup/polaris.sql`：从文本备份重建，旧库先改名保留；
  - 只撤销某一次修改：`polaris undo <batch>`，按修改记录反向写回。
- **表结构升级**：`packages/cli/src/db/migrations/0001_init.sql`、`0002_….sql` 按编号执行，执行前自动备份。不手改数据库。
- **从现在的 JSON 迁入**：`polaris import-json <数据文件夹>`，把旧任务、系统、版本、发版记录、动态原样导入，导入后核对条数和关键字段。
- **兼容**：Artifact 数据库导出的格式也走同一个导入命令。

### 0.4 读取路径（前端不受影响）

- `polaris serve`：本机服务，只监听 127.0.0.1，`/data.json` 每次请求时从数据库查出来组装。格式和现在一样（board、log、tasks），另加 requirements。
- `polaris mirror`：把同样的 JSON 写进页面，生成单文件镜像。
- 前端的数据来源层（第 4 节）不需要知道背后是数据库。

### 0.5 语言与代码组织

> 2026-11-11 实施时调整：插件运行所需的文件集中到 `plugin/`（`.claude-plugin/plugin.json`、`skills/`、`bin/polaris.mjs`、`assets/index.html`），仓库根目录的 `marketplace.json` 以 `./plugin` 为来源，安装时不带源码和依赖；斜杠命令按官方建议写成 `plugin/skills/` 下只能手动调用的 skill。下文的目录树保留设计时的样子。

**全部用 TypeScript，不用 Python。** 一个 pnpm 工作区，分三个包：

| 包 | 内容 | 依赖 |
|---|---|---|
| `@polaris/core` | 共享的类型、枚举（分组、需求状态、优先级…）、校验函数、页面 JSON 格式（Snapshot） | 无 |
| `@polaris/cli` | 命令行：数据库、修改记录、业务规则、导入导出、本机服务、镜像 | `core`；运行时只用 Node 自带模块（`node:sqlite`、`node:http`、`node:fs`、`node:child_process`） |
| `@polaris/web` | 看板前端 | `core`、React、Zustand |

- **命令行发布方式**：用 esbuild 打包成一个文件 `plugin/bin/polaris.mjs`，提交进仓库。插件里的斜杠命令和 Skill 都调 `node <插件目录>/plugin/bin/polaris.mjs …`，装插件的人不用 `npm install`。
- **运行要求**：Node 22.13 以上。启动时检查版本，不满足就给出明确提示。
- **`node:sqlite` 还标着“实验性”**：启动时屏蔽这条提示。所有数据库调用都集中在 `db/` 一层，以后 Node 改接口时只改这一层。

以下是前端工程（`web/`）的设计。

## 1. 现状

`skills/polaris/assets/index.html` 一个文件里装了三部分：

| 部分 | 行数 | 内容 |
|---|---|---|
| CSS | 约 405 行 | 设计变量、页头、卡片、矩阵、分组列表、动态、两种浮层、星图工具条、大字模式 |
| HTML | 约 70 行 | 页面骨架 |
| JS | 约 1440 行 | 见下 |

JS 部分：
- 约 60 个全局函数和变量；
- 一个约 690 行的画布闭包 `bg`，包含：相机、北斗几何、页头测量、北辰星、星团、背景、交互、帧循环；
- 三种数据来源。

主要问题：
- 全局变量互相引用，改一处不知道会牵动哪里。
- 画布和 DOM 互相直接读写，比如画布去量页头元素的位置、点卡片直接调用画布。
- 没有类型、没有单元测试，每次只能靠截图回归。
- 渲染方式是数据一变，整块 `innerHTML` 或节点重建，靠 `same()` 手工比对来避免重画。

## 2. 硬约束

1. **产物仍是单个 HTML 文件**：线上镜像要发布到 claude.ai Artifact，那里有内容安全策略，脚本只能来自几个指定的 CDN、样式只能来自 Google Fonts，所以所有代码和样式都要内联。单文件不超过 16MB，实际预计 300KB 以内。
2. **三种数据来源都要保留**：
   - 镜像里内嵌的数据；
   - 本机 `polaris serve` 提供的 `/data.json`，每 3 秒检查一次；
   - 旧看板的 Artifact 数据库。
3. **不要单独的后端服务**：本机只靠 `polaris` 命令行（Node 自带模块）。
4. **外观和交互与 v41 完全一致**：拆分是重构，不改设计。设计改动另做。
5. 页面要能离线使用：字体加载失败时退回系统字体。

## 3. 技术选型（调研结论）

| 方面 | 选择 | 比较过的方案 | 理由 |
|---|---|---|---|
| 语言 | **TypeScript 7（strict）** | JavaScript | 任务、看板、星图几何都有明确结构；数据文件由多个会话写，类型能在构建期拦住字段错误 |
| 界面框架 | **React 19** | 原生 DOM 分模块、Preact、Lit、Svelte、Vue | 面板、浮层、列表这类界面用组件写最清楚；React + TS 有成熟的生态、类型支持和开发工具链；体积多出约 60KB（gzip 后约 20KB），对单文件不构成问题。Preact 更小但生态和类型差一截；Svelte、Vue 会引入第二套技术栈 |
| 星图画布 | **独立的 TS 渲染引擎，不用框架或库** | three.js、PixiJS、Konva | 现在是 Canvas 2D、约 700 行、60fps 动画，自己的代码完全够用；引入图形库要多带几百 KB，还得重写北辰星的光效。引擎不依赖 React，React 只负责挂载画布并通过接口驱动它 |
| 状态管理 | **Zustand 5** | Redux Toolkit、Jotai、手写 `useSyncExternalStore` | 状态不多：数据、当前系统、筛选、点亮、星图开关、输入方式、大字。Zustand 约 1KB，React 外的画布引擎也能直接订阅，不需要 Provider |
| 样式 | **CSS Modules + 全局设计变量 `tokens.css`** | Tailwind、styled-components、vanilla-extract | 现有 CSS 是手写的“玻璃面板 + 切角 + 霓虹”风格，原样迁移最省、最不容易走样；CSS Modules 由 Vite 内置，按组件拆文件、类名不冲突，运行时没有额外开销 |
| 构建 | **Vite 8 + vite-plugin-singlefile** | webpack、esbuild 手写脚本、Parcel | Vite 开发热更新快；插件把 JS、CSS 全部内联成一个 HTML，正好满足约束 1 |
| 本机开发数据 | **Vite 开发代理把 `/data.json` 转给 `polaris serve`** | 前端自己读数据库 | 数据只有命令行一个读写入口，前端开发时也不绕开它 |
| 代码检查 | **ESLint 10（typescript-eslint、react-hooks）+ Prettier 3** | Biome | 统一类型、代码风格与组件规则，便于贡献者协作 |
| 测试 | **Vitest 5 + Testing Library + jsdom** | Jest | 与 Vite 共用配置；测纯逻辑（筛选、等待天数、几何）和组件行为 |
| 包管理 | **pnpm**，版本全部锁死 | npm | 与现有项目一致 |

## 4. 分层

从下到上：

1. **数据文件**：本机 `data/`，唯一正本。
2. **数据来源适配层** `data/`：三种来源实现同一个接口 `DataSource.subscribe(onData, onError)`，统一输出 `Snapshot { board, log, tasks, origin }`。
3. **领域层** `domain/`：
   - 类型：`Task`、`Board`、`System`、`AppInfo`、`LogItem`；
   - 常量：六个分组、七颗北斗星和分组的对应关系、颜色；
   - 纯函数：按系统过滤、等待天数、“需要你”、下一版候选、完成比例、搜索匹配。

   这一层不碰 DOM，全部有单元测试。
4. **状态层** `store/`：
   - `dataStore`：最新快照和连接状态；
   - `uiStore`：当前系统、搜索词、只看需要我、点亮的星、星图开关、输入方式、大字模式。需要记住的选择存在浏览器本地存储里，读写都包在 try/catch 里。
5. **两个消费方，互不直接调用，只通过状态层和明确的接口交流**：
   - **界面组件** `components/`：React 组件，从 store 读数据、用领域函数算出要显示的内容；
   - **星图引擎** `sky/`：纯 TS 类 `SkyEngine`，自己跑帧循环。
6. **两者的交流方式**：
   - 引擎订阅 store：任务、当前系统、点亮的星、星图开关；
   - 用户在星图里点星时，引擎发事件（`onPickStar`、`onPickDipper`），由界面层处理，比如打开浮层；
   - 页头里画布要避让的元素，由界面组件通过 `LayoutRegistry` 登记，用 `ResizeObserver` 更新位置，引擎只读这份登记，不再自己 `querySelector` 去量。

```
        （每个组件：Xxx.tsx + Xxx.module.css + Xxx.test.tsx）
      hooks/                    useClock、useKeyboard、useFullscreen、useWakeLock、useMediaQuery
      styles/
        tokens.css              颜色、字体、切角等设计变量
        base.css                全局基础样式、大字模式
    tests/
      fixtures/                 示例快照（复用 skills/polaris/assets/sample）
  cli/assets/index.html         构建产物（单文件，提交进仓库，命令行直接用）
```

**拆分原则**：
- 一个文件只做一件事，原则上不超过 300 行；
- 组件只负责渲染和交互，计算逻辑放进 `domain/`；
- 画布代码不 import React。

## 7. 质量保证

1. **单元测试**：
   - 领域函数：分组、等待天数、需要你、发版候选、完成比例、搜索、多系统过滤；
   - 数据来源：三种来源、断线和恢复、内容不变时不重复刷新；
   - 几何：北斗形状旋转缩放后七星相对位置不变（不折勺）、`fit` 不越界、轨道半径不为负。
2. **组件测试**：
   - 卡片点击点亮和再点熄灭；
   - 天枢 / 北辰 / 分组三种浮层的内容；
   - 系统切换；
   - 筛选；
   - 已完成分组的折叠；
   - Esc 按顺序关闭各层。
3. **新旧对照**：用同一份数据，在 1440、1000、960、375 四个宽度下，把新页面和 v41 截图对比，还要逐项核对：
   - 卡片数字；
   - 矩阵格数；
   - 各分组条数；
   - 动态条数；
   - 浮层内容；
   - 星图开关、缩放、方向键；
   - 大字模式、投屏全屏；
   - 控制台没有报错。

   这一步由我在浏览器里做。
4. **门禁**：`pnpm check` 和 `pnpm build` 都通过，产物不超过 512KB（11-11 星图软体拖拽加入后从 400KB 上调）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 画布和页头的位置配合最容易走样：遮罩、小北斗区域、北辰位置 | 先做布局登记，把 v41 的测量规则逐条搬过去并写测试；P2 单独对照 |
| React 重渲染影响 60fps 动画 | 引擎自己跑帧循环，不在 React 渲染里画；界面只在数据或界面状态变化时重渲染 |
| 产物变大 | 约 +80KB，可接受；门禁 512KB（原 400KB，星图功能增多后上调） |
| 旧的手工比对逻辑 `same()` 被去掉后多次刷新闪动 | 来源层在内容不变时不推送；组件用稳定的 key 和 memo |
| 以后改设计时不知道改哪里 | `references/design.md` 改写成“设计规则 → 对应文件”的索引 |
